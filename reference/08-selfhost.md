# 自托管 vs API 的 Break-even 分析（可引用资料包）

> 用途：为「LLM 成本审计 + 降本实施」服务建立可引用、可复现的事实底稿。
> 采集日期：本机会话当日。所有数字均附来源 URL 与性质标注。
> 性质标签：**官方** = 厂商/项目自发布价目或基准页；**论文** = 同行评审或 arXiv 预印本；**第三方实测** = 有方法学说明的第三方基准；**第三方汇总** = 媒体/服务商整理（未逐条回源）；**厂商宣传** = 营销口径，无方法学；**本报告计算** = 由上述两类数据做四则运算得出，公式已写出；**未核实** = 抓取失败或只有标题。

## 0. 一句话结论（可直接对客户说的话术）

| # | 结论 | 依据 |
|---|---|---|
| 1 | 按**满载**算，H100 上 8B FP8 自托管的输出 token 成本约 **$0.042/M**，比 DeepSeek Flash 的 **$0.60/M**（谷时输出价）便宜约 **14 倍** | 本报告计算，见 §3 |
| 2 | 但这 14 倍只在**利用率接近 100%** 时成立。利用率掉到 **7%**，成本就与 API 打平；掉到 5% 就比 API 贵 | 本报告计算，见 §3.3 |
| 3 | 一旦把 **$2,000/月**的运维人力计入，8B 场景需要**持续 1,383 tok/s**（= 满载能力的 5.2%）才能收回人力，折合 **35.8 亿输出 token/月** | 本报告计算，见 §3.4 |
| 4 | 70B 级别自托管的盈亏平衡利用率是 **35%**（对 Together 的 Llama 3.3 70B $1.04/M） | 本报告计算，见 §3.3 |
| 5 | 直接把 8B 从 FP8 换成 INT4，是**省一半的钱、赔上最多 59% 的准确率**的赌注，且中文（非英语）退化更重 | 论文 EMNLP 2025，见 §4 |
| 6 | 「按需租 GPU 更贵」的真正杀手不是时价，是**闲置**：AWS H100 标价 $12.29/GPU·hr，在 5% 利用率下等效 **$245.80/有效 GPU·hr** | 第三方汇总 nOps，见 §5 |

## 2. vLLM / SGLang / TensorRT-LLM 吞吐实测（tokens/s）

### 2.1 NVIDIA TensorRT-LLM 官方基准表（首选可引用源）

来源：<https://nvidia.github.io/TensorRT-LLM/performance/perf-overview.html>（性质：**官方**；页脚标注 last updated 2025-09-15，commit 0c9430e，v0.21）

**方法学（可直接写进报告的方法段，官方原文要点）**：本地推理客户端以无限速率灌请求（请求间无延迟），是**离线最大负载**场景，指标为 `Total Output Throughput (tokens/sec)`；权重用 ModelOpt 量化；KV cache 占用设为 0.95（默认 0.90）。该页自己声明「不应视为 TensorRT-LLM 的峰值性能」，且命令尽量简化以便复现。

> **三个必须对客户讲清的坑（官方表格自身暴露的）**
> 1. **TP 数不同不能直接比**：70B FP4 单卡 B200 就跑到 10,614 tok/s，而 70B FP8 要 2 张 H100 才 6,092 tok/s。按「每卡」算是 B200 的 3.5 倍——但那是 FP4 的功劳，不是 GPU 的功劳。
> 2. **长输入是断崖**：8B 从 (128,128) 的 26,401 掉到 (20000,2000) 的 1,341，**掉 95%**。RAG / 长文档场景不能用短上下文数字报价。（官方）
> 3. **这是离线满载**，没有任何在线 SLA（TTFT/TPOT）约束。对外报价若引用这组数字，必须标注「理论上限」。

### 2.2 dstack 三方框架横向实测（同一模型、两套硬件）

来源：<https://dstack.ai/blog/h200-mi300x-deepskeek-benchmark/>（性质：**第三方实测**，2025-03-18，方法学与源码公开：<https://github.com/dstackai/benchmarks/tree/deepseek-r1-benchmark/Deepseek-R1>）

**配置**：模型 DeepSeek-R1（671B MoE，MLA + DeepSeekMoE）；硬件 A = 8×H200 SXM5 (141GB, 2×Xeon 8570)，硬件 B = 8×MI300X (192GB)；在线用 SGLang 的 `bench_serving.py`（输入长度固定 3200，并发 4→128，输出 800），离线用 vLLM 的 `benchmark_throughput.py`。

| 结论 | 数值 | 性质 |
|---|---|---|
| H200 在线最高吞吐 | **TensorRT-LLM 4,176 tokens/s**（全 8 卡合计） | 第三方实测 |
| H200 离线最高吞吐 | **SGLang 6,311 tokens/s** | 第三方实测 |
| 并发 < 128 时 | vLLM 在线吞吐与端到端延迟领先 | 第三方实测 |
| MI300X 在线最高吞吐 | **vLLM 4,574 tokens/s** | 第三方实测 |
| 并发 < 32 时（MI300X） | SGLang 在线吞吐/延迟胜出 | 第三方实测 |
| TTFT 最优 | H200 + TensorRT-LLM（并发 ≤64 最稳）；MI300X 在并发 128 时 vLLM 最优 | 第三方实测 |
| TPOT 最优 | H200 + vLLM（全并发区间）；MI300X 并发 >32 后 vLLM 领先 | 第三方实测 |
| 前缀缓存 | H200 上开 prefix cache 后 vLLM 在线吞吐/TTFT/延迟优于 SGLang，但 vLLM 的 TPOT 反而升高（作者标注「需进一步调查」） | 第三方实测 |

> **话术**：「框架没有全能冠军。同一个模型、同一批卡，TensorRT-LLM 赢吞吐、vLLM 赢 TPOT、SGLang 赢离线。**先定 SLA（首字延迟还是总吞吐），再选框架**，否则你花在调框架上的时间会超过省下的钱。」

## 3. 折算 $/M token 与 API 单价对比（含交叉点）

### 3.1 计算口径（先声明，避免被客户质疑）

```
理论 $/M 输出token = 每小时租价 / (吞吐 tok/s × 3600)
有效  $/M 输出token = 理论值 / 利用率
```

局限（必须随数字一起给出）：
- 只用 **output throughput**，因此**低估了真实成本**（prefill/输入 token 的算力没计入）；
- 用的是**离线满载**吞吐，不是带 SLA 的在线吞吐，因此**高估了实际可用吞吐**（两个偏差方向相反，净效果不确定）；
- 不含**存储、出口流量、运维人力、冗余/弹性容量**（nOps 给的 TCO 溢价是 +30%~+80%，见 §1.2）。

## 4. 量化（FP8 / INT8 / INT4）对质量的影响证据

### 4.1 论文一：ACL 2025《"Give Me BF16 or Give Me Death"?》

来源：<https://arxiv.org/abs/2411.02355>（性质：**论文**，ACL 2025 接收；作者 Kurtic, Marques, Pandit, Kurtz, Alistarh — Neural Magic / IST Austria）

方法：Llama-3.1 全系列；**500,000+ 次评测**；覆盖学术基准 + 真实任务；量化格式用 vLLM 实测推理性能。

| 结论 | 原话要点 |
|---|---|
| FP8 (W8A8-FP) | **「effectively lossless across all model scales」**——所有规模上实质无损 |
| 调优过的 INT8 (W8A8-INT) | 精度下降**出乎意料地低（1–3%）** |
| INT4 仅权重量化 (W4A16-INT) | **比预期更有竞争力，可与 8-bit 匹敌** |
| 部署建议 | 同步（synchronous）场景 **W4A16 最具成本效益**；异步连续批处理场景 **W8A8 占优**；混合负载取决于具体用例 |

> **可执行的审计建议（直接抄进检查表）**：第一刀砍在 FP8，**几乎零风险**；第二刀砍 INT8，接受 1–3% 掉点；**INT4 要分场景**——同步短请求可用，连续批处理/长上下文不要用。

### 4.2 论文二：EMNLP 2025《Does quantization affect models' performance on long-context tasks?》

来源：<https://aclanthology.org/2025.emnlp-main.479/>（性质：**论文**，EMNLP 2025 main，页码 9422–9470；作者 Mekala, Atmakuru, Song, Karpinska, Iyyer — UMass）

方法：**第一个**针对长输入（≥64K tokens）与长输出任务的量化系统评测；**9.7K 测试样本**；5 种量化方法（FP8、GPTQ-int8、AWQ-int4、GPTQ-int4、BNB-nf4）；5 个模型（Llama-3.1 8B/70B、Qwen-2.5 7B/32B/72B）。

| 结论 | 数值 |
|---|---|
| 8-bit 平均 | 保留精度（**约 -0.8%**） |
| 4-bit 平均 | **大幅掉点，长上下文输入场景最多下降 59%** |
| 语言影响 | **输入不是英语时退化更严重** ← 对中文业务是直接预警 |
| 方法/模型/任务依赖 | 极强。**Qwen-2.5 72B 在 BNB-nf4 下依然稳健，而 Llama-3.1 70B 在同一任务上掉 32%** |
| 作者结论 | 部署量化 LLM 前必须做**任务特定**评测，长上下文与非英语场景尤其如此 |

> **这是整个资料包里最该拿给中文客户看的一段**：4-bit 量化 + 长上下文 + 中文 = 三重叠加的掉点风险。而且**换模型就可能从 -0% 变 -32%**，不能照抄别人的评测结论。

### 4.3 官方表格自带的量化收益证据（性质：官方）

同一张 NVIDIA 表里，FP4 相对 FP8 的收益：
- 70B：FP8 需 **2×H100** 才 6,092 tok/s；FP4 用 **1×B200** 就 10,614 tok/s。
- 即**同样服务 70B，FP4 路径的卡数是 FP8 路径的一半**，代价是 4-bit 精度（详见 §4.1/§4.2 的质量风险）。

## 5. 什么情况下自托管反而更贵

### 5.1 空闲率（第一杀手）

来源：<https://www.nops.io/blog/cloud-gpu-pricing-optimization/>（性质：第三方汇总）

| 事实 | 数值 |
|---|---|
| GPU 按**开机时长**计费，不按利用率 | 「GPU instances bill for uptime, not utilization」 |
| AWS H100 标价 $12.29/GPU·hr，在 **5% 利用率**下 | 等效 **$245.80 / 有效 GPU·hr** |
| 8 卡 p5 按需 24h 闲置（1 小时/天训练） | 日成本 $2,359.68 → 单小时有效成本 **$294.96/GPU·hr** |
| 按需 vs 预留的盈亏平衡 | **1 年预留：60–65% 利用率**；**3 年预留：50–55%** |
| 若利用率低于 60% | 「按需 + 激进生命周期管理」更便宜 |

### 5.2 运维人力与工程成本

- **本报告设定值**（请用客户真实工资替换）：$2,000/月 → 见 §3.4(b) 的交叉点计算。
- 抢占实例的**工程代价是硬性的**（第三方汇总，Introl）：
  - 必须实现 checkpoint（建议每 10–30 分钟）
  - 必须实现终止通知处理（AWS 2 分钟 / GCP 30 秒窗口）
  - 必须跨 10–15 种实例类型、多个可用区/区域做多样化
  - 单次中断损失 10–30 分钟进度；示例中按 **20% 开销**计入
  - 非生产环境要建 staging 做中断恢复演练
- **框架侧的隐性人力**（第三方实测，dstack）：同一批卡上 vLLM / SGLang / TensorRT-LLM 各赢不同的指标，且 vLLM 的 prefix cache 在 H200 上出现了 TPOT 反而升高、作者标注「需进一步调查」的现象——说明调优不是一劳永逸的工程。

### 5.3 突发扩容 / 弹性

来源：nOps 与 Introl（均为第三方汇总）

| 风险 | 数值/事实 |
|---|---|
| AWS us-east-1 的 H100 spot 可用性 | 在一天内波动于 **0–60%**；spot 耗尽时只能回落按需 |
| GCP 抢占 VM | **24 小时强制回收一次**（哪怕容量充足） |
| Azure | **没有真正的 spot**；Low Priority 只省 20–30% |
| 亚太/欧洲区域价格 | 比美东高 **10–25%** |
| 新云厂商 SLA | 95–98%，而 hyperscaler 是 99.95–99.99%；多数无 HIPAA/SOC2/FedRAMP/ISO 27001 |
| 合规 | 受监管行业**不能**用新云 GPU 跑生产（无合规认证） |
| 存储/出口 | 出口 $0.08–0.12/GB；checkpoint 累积（示例：10TB checkpoint = S3 $230/月常年存在） |

### 5.4 定量反例：等预算比较下 API 全胜（可引用的学术级反方证据）

来源：<https://zenodo.org/records/21195375>（性质：**论文/预印本**，Zenodo 发布 2026-05-14，DOI 10.5281/zenodo.21195375，University of Alabama in Huntsville；**样本小，作者自己声明不足以做总体结论**）

方法学创新（值得学）：**等预算比较（equal-budget）+ 拒绝感知（refusal-aware）**——固定两侧的每日花费上限，问"同样预算下各能服务多少次查询"。作者指出业界通病：**"日限额的 API 服务" 对比 "无限额的自托管机队"，比的不是同一种服务**。

| 结论 | 数值 |
|---|---|
| 75K MAU 的地理问答负载，等预算比较 | **API 在每个被评估的配置下每美元服务查询数都最多**（未做质量差调整前） |
| 自托管仍有竞争力的边界场景 | ① 供应商非线性定价的专用模型 ② 硬数据驻留要求 ③ 已有相邻业务的 GPU 基础设施 |
| **更重要的发现** | **工具返回值的架构设计（tool-return design）比"托管方式"更影响成本** |
| templated vs 原始 payload | 每查询 **2.3× – 6.2×**；配对实测 **8.8×**（Table 4） |
| 75K MAU 月成本 | 激进模板化 **$11,309/月**；真实关键字段模板化预计 **$17K–36K/月**（3× 中位数约 $33K，标注为推算）；原始 freeform 压力测试 **$99,398/月** |
| 另一组（2026-06-04，6 个测量单元 / 2,832 次调用） | 「周期模式」杠杆 **1.3–1.7× per cycle**；「预检 LLM 闸门」在 f_naive ≥ ~16% templated / ~6.6% freeform（无恢复极限）时更便宜，交叉点随恢复率上升而升高、最终消失 |
| 计算器 | <https://calc.ajinkya.ai>；代码 <https://github.com/ajinkya/ai-cost-calculator-studio>（原始链接：<https://github.com/ajinkyakulkarni/ai-cost-calculator-studio>） |

> **对服务的直接启示（可写进提案）**：**先改架构，再谈自托管。** 一个 8.8 倍的架构杠杆（工具返回值模板化）比任何 GPU 议价都值钱。审计顺序应当是：**① 工具返回值/上下文设计 → ② 模型档位与缓存 → ③ 批量化 → ④ 才是自托管 vs API。**

## 6. 交付：客户检查表（本资料包可直接转成的产物）

**阶段 A：先证伪自托管（先算，不要先买卡）**
1. 客户过去 30 天的**月输出 token 总量**是多少？（用账单，不要用估计）
2. 是否有**稳定负载**？画出 24 小时 × 7 天的 QPS 曲线。峰值/均值比 >3 的，自托管基本出局。
3. 用 §3.4(a) 表查出**交叉点利用率**，与客户实际负载率对比。
4. 用 §3.4(b) 把客户实际人力成本代进去，算出「收回人力所需的月输出 token」。

**阶段 B：量化能不能砍（先砍 FP8）**
1. 现用精度是什么？→ 评估 **FP8**（论文一：所有规模实质无损）。
2. FP8 无收益或还想再砍 → 评估 **INT8 W8A8**（接受 1–3% 掉点）。
3. 想上 **INT4** → 必须先做**客户自己的**任务评测（论文二：模型/方法/任务依赖极强；长上下文 4-bit 最多掉 59%；非英语更严重）。
4. 长上下文 + 中文业务 → **不要上 4-bit**。

**阶段 C：架构降本（比自托管回报高）**
1. 工具返回值/上下文模板化（论文：2.3–8.8× 杠杆）。
2. 缓存命中率（缓存输入价是标准的 2%–10%）。
3. 批量 API（-50%）。
4. 谷时调度（DeepSeek 谷时 -50%；UTC 峰时为周一至周五 01:00–04:00、06:00–10:00）。
5. 模型路由/级联（小模型 API 输出价已到 $0.50/M）。

**阶段 D：确认要自托管才走**
1. 计算可接受的**空闲率**成本（§5.1：5% 利用率 = 等效 20 倍单价）。
2. 是否用 spot？→ 接受 H100 **4.1%/小时**的中断率 + checkpoint + 终止处理器（§1.3/§5.2）。
3. 选框架：**先定 SLA**（TTFT 还是总吞吐），再选 vLLM / SGLang / TensorRT-LLM（§2.2）。
4. 长上下文场景必须用长输入数字报价（§2.1 坑 2：8B 长输入吞吐只剩 5%）。
5. 冗余/突发容量：spot 可用性 0–60% 波动（§5.3），峰值必须留按需兜底。
