# 浪费矩阵总表（W1–W18）

> 来源：2026-10-22 深调研 + 本机自审实测
> 本文件是浪费项总表，逐项链接到对应 reference 文件

**怎么用**：拿到客户账单后从上往下逐行跑。每行的「判据」决定它是否命中，「怎么量」给出这一行必须用到的数据与公式，「值不值得做」给出动作结论与一句理由。**没命中就写「未发现」——那也是结论。**

**证据等级只用这五个词**（含义见 [00-index.md](00-index.md) 第一节）：`官方` / `论文` / `第三方实测` / `厂商宣传` / `未核实`。
本表中「第三方实测」包含本机自审账本实测（委托方＝被执行方，程序写入、非厂商口径）。
**「厂商宣传」标签的数字不得当作独立证据**，只能当线索；本表凡涉及处均在同一行注明。
编号 W1–W11 沿用自审报告的编号，W12 起为本轮补入的、自审未覆盖但 reference 有据的项。「详见」指向本技能库内的证据文件（reference/ 或 templates/）。

## 二、不建议做的项（客户最容易在这里被忽悠）

以下 4 项判为**不建议做**。共同特征：看着像省钱机会，实际要么没有可引用的数据支撑，要么省的钱小于风险。**竞品只告诉你「你能省」，只有你把「这里别省」写出来**（来源：templates/report-template.md §5）。

|---|---|---|

## 四、六类杠杆不能相加（纪律条款）

修法杠杆固定为 6 项（来源：templates/report-template.md §4.5）：**① model routing ② semantic caching ③ prompt caching ④ prompt compression ⑤ batch routing ⑥ provider arbitrage**；另有两个容易漏的：错峰调度、结构杠杆（输出砍半、上下文剪枝）。

**纪律：各杠杆的百分比不可累加。** 把「路由省 85% ＋ 缓存省 90% ＋ 批处理省 50%」加成一个数，是本行业最容易被客户当场戳穿的错误。五条理由：

1. **分母不同**：每个百分比针对的成本子集不同（某 tag / input 侧 / 总账），**禁止写百分比而不给分母**（来源：templates/report-template.md 表 5 规范）。
2. **叠加没有条文**：「批处理 × prompt caching 能否叠加」，四家厂商全部「未核实」，官方文档无明文；只能在实施阶段用一次 A/B 小批实测确认（来源：reference/05-batch.md）。
3. **杠杆会互相反杀**：路由到更便宜但缓存冷的模型，单步成本反而约为原来的 5 倍；只有当目标模型的未缓存输入价 > 当前模型 10 倍时才划算（来源：reference/04-routing.md）。
4. **identified ≠ realized**：逐项相加得到的是已识别上限，不是账单数字；不排除厂商降价（推理成本约每年降 10 倍），「什么都没做」也能被报成自己的功劳（来源：templates/report-template.md §4.5）。
5. **只承诺可验算的部分**：只承诺 quick win ＋ batch/缓存 ＋ 规则 routing，保守区间 **40–60%**，因为每一项都有官方单价支撑、客户能自己验算（来源：templates/report-template.md §4.5）。

**正确做法**：逐项单独报告并标注基数与证据等级；要报合计时，用「在同一份基线上重算的联合反事实」，而不是把百分比相加；合计不得高于单项最大杠杆，也不得高于 100%。**能相加的是钱，不是百分比。**
