# 第 3 步：LLM 成本审计 · 交付模板

> 建立 2026-10-22
> 用途：这是 **付费审计服务的交付物**。报价口径**以 SKILL.md 为准**：首单 **$300–800 固定价**；只有客户月 API 支出超过 **$5,000** 才谈「按已验证节省的 15–20% 分成」。客户付钱买的就是这份报告。
> 配套：产品定义与落地页见 [出海-LLM成本审计-产品与落地页-20261021.md](出海-LLM成本审计-产品与落地页-20261021.md)

## §0 这份模板解决什么问题

你没有案例背书，所以你的可信度只能来自**两样东西**：

1. **方法透明** —— 第 6 章把算式和假设全写出来，客户能自己复核
2. **敢说不** —— 第 5 章明确列出「**不建议做**」的项

**这两章是模板的骨架，别省。**

## §1 客户资料清单（Intake）— 发给客户的第一封邮件就用它

**要的（缺一不可）：**

| # | 要什么 | 为什么 |
|---|---|---|
| 1 | 近 **1–3 个月**的 API 账单 / 用量导出（CSV） | 一切的基线 |

## §2 计算方法（不写代码，用表格就能跑）

### 表 1　账单归一化

把各家的导出拼成一张表，列固定成这样：

| date | provider | model | tag / endpoint | requests | input_tokens | cached_input_tokens | output_tokens | cost_usd |
|---|---|---|---|---|---|---|---|---|

**要点：**

- `tag` 列没有就填 `untagged`——**别丢行**
- 各家字段名不同（`prompt_tokens` / `input_tokens`），统一到上面这套
- 有 `cost_usd` 就用供应商给的；没有就用表 2 自己算

### 表 2　单价表（每百万 token 单价）

| provider | model | input / Mtok | cached input / Mtok | output / Mtok |
|---|---|---|---|---|

⚠️ **单价必须现查供应商官网当天的价格页**，截图存档（写进第 6 章）。价格过期是这类报告最容易被挑错的地方。

### 表 3　按维度汇总（把表 1 做透视）

对 `provider` / `model` / `tag` **各做一遍**：

| dimension_value | cost_usd | % of total | requests | cost_per_request |
|---|---|---|---|---|

**这一张表就是报告的「Spend Map」。**

### 表 4　单位经济

| 指标 | 公式 |
|---|---|
| 成本 / 请求 | 总成本 ÷ 总请求数 |
| 成本 / 用户 | 总成本 ÷ 客户给的用户数 |
| input : output 成本比 | input 成本 ÷ output 成本 |
| **缓存命中率** | cached_input_tokens ÷ input_tokens |
| 平均 input tokens / 请求 | 总 input ÷ 总请求 |

### 表 5　发现清单（Findings）

| id | finding | evidence | est. saving / yr | confidence | effort | priority |
|---|---|---|---|---|---|---|

**规范：**

- `evidence` **必须指向具体行列**（例：`tag=summarize 占 41% 成本，其中 92% 走旗舰模型`）
- `confidence` 只允许三档：**Measured（算出来的）/ Estimated（估的）/ Needs test（要试）**
- **禁止写百分比而不给分母**

### 表 6　路线图

按 **saving ÷ effort** 排序，不按 saving 绝对值排。

## §4 ⭐ 浪费清单（**这是产品的真正内容**）

对每一条，先**在所有维度里找它**，找到才算。**没找到就写「未发现」——这也是结论。**

---

### W1　模型超配

**怎么发现**：按 `tag` 看**模型分布**。若某个低复杂度功能（分类、抽取、改写、翻译）100% 走旗舰模型 →

**证据长这样**：`tag=classify 占 18% 成本，其中 100% 走旗舰模型；同类任务在小模型上的公开基准差距 <2 分`

**修法**：路由到小模型；**先跑 200 条影子对比（shadow eval）再切**

**典型幅度**：该功能成本的 **60–80%**

**confidence**：Needs test（必须做质量对比）

---

### W2　固定前缀未缓存

**怎么发现**：算 **缓存命中率**（表 4）。若平均 input 很大但缓存命中率 ≈ 0 →

**证据**：`平均 6,400 input tokens/请求，但 cached_input_tokens = 0`

**修法**：开启 prompt caching（主流厂商缓存命中的 input 通常便宜 **75–90%**）；对**确定性请求**再加一层结果缓存

**典型幅度**：**input 成本降 50–90%**

**confidence**：Measured（账单直接算得出）

---

### W3　上下文过长

**怎么发现**：对比**平均 input tokens** 与「这个任务实际需要的信息量」。整篇文档塞 prompt、RAG 一次召回 20 条 →

**证据**：`tag=qa 平均 12,000 input tokens，但回答只引用其中 1 段`

**修法**：检索裁剪（top-k 收紧）、先摘要再喂、分块

**典型幅度**：**input 成本降 40–70%**

**confidence**：Measured + Needs test

---

### W4　输出无上限

**怎么发现**：看 **output/input 比**；检查代码里有没有 `max_tokens`；提示词有没有「简洁」约束

**证据**：`tag=extract 平均 output 1,800 tokens，但目标字段只有 6 个`

**修法**：设 `max_tokens`；加显式长度约束；用结构化输出

**典型幅度**：**output 成本降 20–50%**

**confidence**：Measured

---

### W5　失败与重试浪费

**怎么发现**：需要**错误日志**。没有的话，**从账单侧估**（请求数 vs 成功数）。公式：

> 浪费 = 失败请求数 × 平均单请求成本 × 平均重试次数

**修法**：schema 校验前置、指数退避、幂等键、把「重试」和「新请求」分开打标

**典型幅度**：**5–15%**

**confidence**：Estimated（日志缺失时标注）

---

### W6　可批处理却走同步

**怎么发现**：找**离线/非实时**任务：批量嵌入、历史数据回填、离线摘要、夜间批分类。这些不需要秒级响应 →

**修法**：走 Batch API（主流厂商通常约 **50% 折扣**）

**证据**：`tag=embed_backfill 占 22% 成本，延迟容忍度 24h，却走同步接口`

**典型幅度**：**该部分成本的 ~50%**

**confidence**：Measured

---

### W7　环境未分离

**怎么发现**：账单里能看出**开发/测试流量**吗？有没有按环境打标签？通常能看到「无 tag 的请求占 X%」

**修法**：按环境/团队打 tag，分离密钥，设配额

**典型幅度**：**3–10%**（金额不大，但**它带来可见性——后面所有优化的前提**）

**confidence**：Measured

---

### W8　重复嵌入

**怎么发现**：向量库 / embedding 调用的**重复内容比例**。同一段文本每次重新嵌入 →

**修法**：内容哈希去重 + 结果缓存

**典型幅度**：**嵌入成本降 30–80%**

**confidence**：Measured

---

### W9　Agent 循环失控（附加）

**怎么发现**：**单次用户请求的模型调用次数分布**（尾部很重要）

**修法**：步数上限、预算上限、工具调用熔断

**典型幅度**：差异极大，但**尾部请求常常吃掉 30%+ 成本**

**confidence**：Measured

---

### W10　超长 preamble / 重复工具定义（附加）

**怎么发现**：prompt 模板的固定部分 token 数 × 请求数

**修法**：压缩模板、把重复工具定义移到缓存段

**典型幅度**：**5–20%**

**confidence**：Measured

---

### W11　上下文膨胀（2026-10-22 新增，我的实测项）

**怎么发现：**

1. 算 **平均上下文 = (input_tokens + cached_input_tokens) ÷ 请求数**。**超过 10 万 token 就是命中。**
2. 看两个数：**单任务调用次数**（>30 次即命中）、**长任务里有多少次调用**。
3. **根因公式：消耗 = 平均上下文 × 调用次数。** 两个因子各自超标 3–10 倍，乘积就超标几十倍。

**怎么定位钱花在哪类内容上**：按类别统计进入上下文的字符占比。我自己那次的实测：

| 类别 | 占比 |
|---|---|
| 工具返回（抓网页 / 读文件） | **60.7%** |
| reasoning / 思考全文 | **25.8%** |
| 工具调用参数 | 10.7% |
| 助手正文 | 2.8% |
| **用户消息** | **0.0%** |

**→ 撑爆上下文的是机器产生的内容，不是客户说的话。** 这一页在报告里冲击力最大。

**修法（按性价比排序）：**

| 修法 | 说明 |
|---|---|
| 大内容落盘，上下文只留摘要 + 路径 | 抓取全文 / 大文件 / 长中间产物 |
| 单任务拆会话 | 超过约 30 次调用就换新会话 |
| 探索隔离到子任务 | 调研试错让子任务烧自己的上下文 |
| **控制内容进入上下文之前** | **不要指望自动压缩** |

**典型幅度**：上下文从 15 万降到 5 万 → **输入 token 直接降 2/3**（缓存读取同比例下降）

**confidence**：Measured（单会话实测）

**⚠️ 必须同时写进报告的反直觉结论：缓存命中不是问题，是好事。**
我自己实测缓存命中率 **96.8%**（缓存读取 1,970.99M vs 新输入 65.22M）。
看到「重发」就去「修缓存」是**错误方向** —— 要降成本只能降上下文长度。

## §4.5 修法杠杆（6 项，同行已验证的清单）

一个在运营的同类服务把实施手段固定为这 6 项
（来源：[llmcfo.com/terms](https://llmcfo.com/terms)，条款 2026-04-24 版）。
你的报告在「修法」一栏里应能对上其中至少一项：

| # | 杠杆 | 一句话 | **量化幅度（带来源）** |
|---|---|---|---|
| 1 | **model routing** | 简单请求走便宜模型 | 级联路由：**省 85%**（MT-Bench，保 95% GPT-4 质量，仅 14% 走强模型，RouteLLM/ICLR2025）；FrugalGPT 最高 98%、平均 50–98%；价差锚：GPT-4o $2.50/M vs mini $0.15/M = **16 倍** |
| 2 | **semantic caching** | 语义相近的请求复用答案 | **只有相对值**：命中率 +1.71x（SISO）。**绝对命中率无权威公开数，必须按客户日志实算** |
| 3 | **prompt caching** | 固定前缀命中前缀缓存 | **DeepSeek 官方**：命中 $0.003 vs 未命中 $0.15/M（flash 错峰）→ **省 98%**；v4-pro $0.022 vs $0.66 → **96.7%**。**Anthropic**：读 0.10x（省 90%）、写 1.25x（加价 25%）、TTL 仅 5 分钟 → **约 1.4 次读取回本**。**OpenAI** 读 0.50x（省 50%，写入免费）；**Gemini** 0.25x（省 75%，限 32K+/TTL≥1h）—— 这两家为**第三方转述，官方页 403** |
| 4 | **prompt compression** | 压缩提示词、去冗余 preamble | LLMLingua（EMNLP2023）最高 **20x** 压缩 —— **这是上限值，不可当承诺** |
| 5 | **batch routing** | 能等结果的走批处理 | **已核实**：Azure 官方原文「50% less cost than global standard」，24h 目标 |
| 6 | **provider arbitrage** | 同一模型换更便宜的供应商 | **无可靠的实时价差表**（未抓到）。⚠️ **见下方「建议不接」** |

**另外两个容易漏的杠杆：**

- **错峰调度**：DeepSeek 的 peak 价仅为 UTC 周一至五 01–04、06–10 两段，**其余时间价格是 peak 的一半 → 省 50%**。
- **结构杠杆（我自己的推算，需在报告里标为推算）**：输出单价约为输入的 3–4 倍 → **输出砍半 ≈ 省 25–35%**；
  平均上下文 15 万 → 3 万 ≈ **省 50%+**。

**按工程量归类：**

| 归类 | 包含 |
|---|---|
| **quick win（一天内）** | 输出上限、去 preamble、上下文剪枝、prompt 前缀重排、错峰调度 |
| **一周内** | batch、语义缓存、prompt 压缩、规则版 routing |
| **结构性改造** | 级联 routing、arbitrage 实施、微调/蒸馏、自托管 |

### ⚠️ 三类不建议接（个人交付者尤其）

| 不接 | 理由 |
|---|---|
| **微调 / 蒸馏** | 要碰客户训练数据和评测集，交付风险与报价量级不匹配 |
| **自托管** | break-even 条件对客户基础设施依赖太重，算错就是你的责任 |
| **provider arbitrage 实施** | 没有可靠的实时价差数据支撑承诺 |

**→ 报价时只承诺前 3 步（quick win + batch/缓存 + 规则 routing），保守区间 40–60%。**
这个区间的好处是：**每一项都有官方单价支撑、客户可以自己验算**。

**W1–W11 加这 6 项 = 17 项检查矩阵。**

### ⚠️ 报告必须给两个节省数字（可信度的核心）

| 概念 | 定义 | 怎么报 |
|---|---|---|
| **已识别节省（identified）** | 一项建议**在动手之前**推算的降幅 | 标注「估算」，写清假设 |
| **已实现节省（realized）** | 改动上线后**真正落进账单**的降幅 | 对照**锁定基线**并与**原始账单对账** |

> 「已识别节省写在幻灯片上；已实现节省出现在账单里，而这两个数字极少相同。」
> —— [multicloudoptimization.com](https://multicloudoptimization.com/blog/measuring-realized-versus-identified-savings/)

**四条必须写进报告的防线：**

1. 先锁定**参与前基线**（「什么都不做本来会花多少」）
2. 与**原始供应商账单**对账，不认估算
3. **排除厂商降价** —— 推理成本约每年降 10 倍（[a16z · LLMflation](https://a16z.com/llmflation-llm-inference-cost/)）；
   不排除的话，「什么都没做」也能报成自己的功劳
4. **不省不收费**（如果你敢承诺）

### ⚠️ 报告第一页必须声明「诊断深度」

| 层级 | 能回答 | 客户需付出 |
|---|---|---|
| **结构性诊断** | 钱在哪个模型 / 项目 / 哪一天 | 账单 + 只读 key |
| **行为性诊断** | 钱在哪次调用 / 哪个功能 / 哪个租户 | 必须加网关或埋点 |

**原因**：厂商 Usage / Cost API 只到「天 × 模型 × 项目 / key」，**永远到不了单次调用**。
不预先说明，客户会觉得这份报告很浅 —— 而这是它本该有的深度。

## §5 ⭐ 「不建议做」怎么写（建立可信度的那一页）

**这一页要列出你**看过但**认定不值得改的项**，并说明为什么。例如：

| 看起来像浪费 | 实际结论 | 理由 |
|---|---|---|
| 30% 成本走旗舰模型 | **不建议改** | 这些请求都是**面向用户的高价值交互**，降到小模型会损失质量；省的钱 < 风险 |
| 用了向量库，看起来贵 | **不建议改** | 嵌入成本只占 3%，替换带来的工程量不划算 |
| 输出 token 偏多 | **建议** | 见 W4——这一条**值得改** |

**为什么这一页值钱**：所有竞品只告诉你「你能省」，**只有你告诉他「这里别省」**。这一页是客户信你下一单的原因。

## §6 ⭐ 方法附录（客户能自己复核）

**必须包含：**

1. **算式**：每一条发现的公式（照抄上面 W1–W10 的公式）
2. **单价来源**：具体到「哪个官网、哪一天、哪个页面」，**附截图**
3. **假设清单**：例如「年化按审计期间 × 12 估算」「错误率用日志中 4xx/5xx 比例代理」
4. **数据局限**：例如「未提供错误日志，故 W5 为估算」「无环境标签，故 W7 只能给下界」
5. **复核指引**：告诉客户「用哪张表、哪几列，能复算出第 X 页的数字」

**这一段就是你的护城河。** 竞品不会写，因为他们不敢让客户算。
